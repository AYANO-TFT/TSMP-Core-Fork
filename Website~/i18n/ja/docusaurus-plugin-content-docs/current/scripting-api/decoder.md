# `TSMPDecoder`

## ヘッダーと本文の直接出力

`useCombinedByteOutput` の既定値は `true` です。予測経路では対応コーデックが復元済みの56バイトヘッダーと本文を専用の RGBA8 readback テクスチャへ直接出力し、別の結合パスと本文の中間出力を省きます。元画像のスナップショット、ヘッダー CRC 検証、長さの完全一致と同じ画像でのフォールバックは維持されます。送信データグラムは変わらず、一定の受信率を保証する機能ではありません。

シェーダーが `_TSMPHeaderTex` と `_TSMPHeaderPixels` の両方を実装すると使用できます。未対応の既存コーデックは別の結合パスを使用します。比較用の設定は Diagnostics > Advanced Decode にあります。`combinedByteOutputCount` は投入回数であり、後から拒否・再処理された予測も含みます。受信フレーム数ではありません。`ResetDecodeDiagnostics()` でリセットします.

`TSMPDecoder` は、TSMP テクスチャを読み取り、ヘッダーを検証し、選択されたコーデックにペイロード バイトを回復するように要求し、変数/RPC メッセージをバインドされた動作に適用します。

このページは、カスタム レシーバーの配線、診断の読み取り、またはフレームが無視された理由のデバッグを行うときに使用します。

## コンポーネントフィールド

| 分野 | 目的 |
| --- | --- |
| `sourceTexture` | エンコードされた TSMP フレームを含むテクスチャ。 |
| `payloadByteTexture` | ペイロード バイトをデコードするときにコーデック シェーダによって使用されるテクスチャをレンダリングします。 |
| `codecHandlers` | デコーダで使用できるコーデック コンポーネント。ヘッダー `codecId` はハンドラーを選択します。 |
| `applyEveryFrame` | コンポーネント更新ループからデコードを実行します。別のスクリプトが `DecodeNow()` を呼び出すときは無効にします。 |
| `skipDuplicateFrames` | 現在のストリームの重複・古いフレームを除外します。Inspector 表示は Filter Frames です。 |
| `frameWindowSize` | Window Size。既定256フレーム、実効最小値1。フレーム0の再開判定に使用し、バッファは確保しません。 |
| `flipY` | 画像を反転するキャプチャ パスのテクスチャ サンプリングを反転します。 |
| `useHeaderPayloadLayout` | ヘッダー ペイロード メタデータを使用してリードバックのサイズを決定します。通常の使用では有効にしておいてください。 |
| `payloadBytesOverride` | テスト パスの手動ペイロード バイト数。 |
| `decodeSafetyMode` | 変形したフレームまたは部分的なフレームのための追加のガード。 |
| `usePredictedReadback` | 既定 true。前回検証した設定でヘッダーと payload をまとめて読み取ります。手動レイアウトと安全モードでは使用しません。 |

`TSMPSetup` は通常、`sourceTexture`、バイト テクスチャ、コーデック ハンドラー、およびバインディング配列を割り当てます。

## ヘッダーの検証

次の場合、デコーダは payload メッセージを適用する前にフレームを拒否します。

- マジックバイトはTSMPではありません。
- ヘッダー サイズはサポートされていません。
- メジャー プロトコル バージョンはサポートされていません。
- ヘッダーの CRC が一致しません。
- ペイロード サイズが利用可能なテクスチャ レイアウトを超えています。

CRC エラーは警告として記録されます。これは、不正なデータを適用せずにキャプチャの破損を特定するのに役立ちます。

## `DecodeNow()`

```csharp
public void DecodeNow()
```

現在の画像をキャプチャし、非同期デコードを開始します。`applyEveryFrame` が無効でも呼べますが、コンポーネントは有効である必要があります。readback が保留中なら新しい処理を開始しません。

初回とフォールバック経路では次の順序で実行します。

1. 現在の入力画像を decoder のスナップショットへコピーします。
2. スナップショットからヘッダーピクセルを読み取ります。
3. マジック、バージョン、ペイロード レイアウト、および CRC を検証します。
4. `codecId` でコーデック ハンドラーを選択します。
5. 同じスナップショットからペイロードバイトをデコードします。
6. ネットワークメッセージを解析します。
7. 変数を適用し、RPC 呼び出しをディスパッチします。

## 予測 readback {#predicted-readback}

有効なヘッダーを学習した後は、CPU がヘッダーを待たず、前回の設定で現在の画像の Luma4 ヘッダーパスと payload パスを実行できます。復元バイトを専用の linear RGBA8 ターゲットにまとめて1回だけ readback します。元画像のスナップショットは Float32 のままで、整数へ復元済みのバイトだけを RGBA8 に保存します。

現在のヘッダーの magic、version、size、CRC と通常のフレーム順序検査を通過する必要があります。CRC より前のバイトは、フレーム番号・時刻・payload 長を除いてキャッシュと一致する必要があります。payload 長は別途**完全一致**を検査し、解釈後の block/sample/start-block 設定も比較します。長さの増減、コーデック・オプション・ストリーム・レイアウトなどの変更があれば、推測した payload を破棄し、**同じスナップショット**から実際の payload を要求します。元画像は再キャプチャしません。CRC 不一致では、未検証データへフォールバックせずフレームを破棄します。

長さの完全一致により、カスタムコーデックへ多くのバイトを要求した場合も同じ先頭データが得られるとは仮定しません。既存のコーデック API とシェーダーは変更せず、各パスの `PrepareDecode` も呼び出します。無効化、入力サイズ・向きの変更、手動レイアウト・安全モードの使用後はヘッダーを再学習します。結合リソースがなければ逐次経路を使います。マテリアルは Editor とビルド準備で自動設定し、通常 Unity の実行時生成ではパッケージのリソースから読み込みます。

内部 readback バッファの `0..55` はヘッダー、`56` 以降は予測 payload、残りは行パディングです。**送信データグラムの変更ではありません。** 追加 GPU ターゲットは14x1のヘッダーと、幅 `min(256, ceil((56 + payloadBytes)/4))` に必要な行数を持つ結合テクスチャで、1ピクセル4バイトです。再利用し、無効化・破棄時に解放します。同時に処理する画像は引き続き1枚です。

`predictedReadbackCount` は採用した予測 payload 数で、RPC の実行成功数ではありません。`predictionFallbackCount` は有効なヘッダーで予測不一致となりフォールバックした回数です。Runtime Status に表示されます。重複・古いフレームでも推測 GPU 処理が実行済みの場合はありますが、メッセージを解析・適用しません。60Hz 配送は保証せず、適用率・遅延・RPC 実行率を個別に測定してください。

## 入力スナップショット {#input-snapshot}

Inspector に追加の参照やモードを設定する必要はありません。decoder は入力と同じサイズの linear `ARGBFloat` RenderTexture を所有し、処理間で再利用して無効化・破棄時に解放します。サンプリングした入力値に8ビット・half-float の量子化を追加しないための選択です。Float32 レンダーターゲットが必要で、形式・割り当てに失敗した場合はデコードを拒否し、既存のエラーログ方針に従って `lastError` を通知します。更新中の元画像へのフォールバックはありません。

追加メモリは `width * height * 16` バイトです。640x360 で約3.52 MiB、1920x1080 で31.64 MiB、3840x2160 で126.56 MiBになります。開始したデコード処理ごとに入力全体を1回コピーし、後で CRC・重複検査により拒否される試行にもこの費用がかかります。CPU readback は追加しません。GPU コピー費用は配布先の実機で測定してください。

キャプチャ後に `sourceTexture` を差し替えたり破棄したりしても、現在の処理の画像は変わりません。変更は次の処理へ反映されます。decoder の無効化は進行中の処理を取り消し、再有効化後に届いた古いコールバックも破棄してから次のデコードを開始します。native と Udon の両方で、ヘッダー・LUT 準備・payload に同じスナップショットを使います。カスタムコーデックは渡された画像を読み取り専用として扱い、恒久的なフレームコピーとして保持しないでください。フレームの逆順や変数・RPC のトランザクション適用を解決する機能ではありません。

## ウィンドウとフレーム順序 {#frame-window}

フィルターが有効な場合、受信番号 `N` と現在のストリームで最後に適用に成功した番号 `P` を比較します。実効ウィンドウは `W = max(1, frameWindowSize)` です。変更は次のヘッダー判定から反映されます。

1. 適用履歴がない場合、または `StreamId` が異なる場合は、順序を比較せず候補を許可します。
2. `N == P` は重複として除外します。
3. `D = (N - P) modulo 2^32` を計算し、`0 < D < 2^31` なら番号の正常な周回も含めて新しいフレームとして許可します。
4. それ以外でも `N == 0` かつ `P >= W` なら再開と推定して許可します。
5. 残りは古い、または順序が不明なフレームとして除外します。UInt32 範囲のちょうど半分の差も、フレーム0の再開例外を除き拒否します。

許可は payload 処理へ進むという意味で、無条件の適用ではありません。ネットワークフレームの適用成功時だけ基準ストリームと番号を更新します。壊れた payload、取り消した要求、ヘッダー/readback 専用安全モードでは基準を更新しません。重複・逆順で除外した場合は従来の重複処理と同様に `lastFrameValid=true` です。`skippedDuplicateFrameCount` と `skippedOutOfOrderFrameCount` に別々に集計し、`lastError` に状態を表示します。推測したバイトデコード・readback が完了済みでも payload メッセージの解析・実行は行いません。

`W=256` では `100 -> 101 -> 100` の最後の100を除外し、`255 -> 0` は拒否、`256 -> 0 -> 1` は再開と後続フレームとして許可します。`4294967295 -> 0` はウィンドウによらず正常な周回です。`W=512` では `256 -> 0` を拒否します。ウィンドウはフレーム数のしきい値であり、時間、スライディング履歴、保存するテクスチャの集合ではありません。

セッション ID のない推定規則です。遅れて届いた過去の0を再開と誤認する場合があり、再開時の0が欠落した場合や1ウィンドウ未満での再開はこの例外では検出できません。リセット受理後は大きな番号の過去フレームも新しく見える可能性があります。別ストリームは許可し、適用成功時に基準を置き換えますが、過去のストリーム履歴は保持しません。RPC イベントの重複判定は変更・初期化しません。`skipDuplicateFrames` を無効にすると重複・順序判定と再開規則をすべて迂回します。録画のシークに使えますが、過去の変数値も再適用されます。

### データグラム互換性

データグラムとプロトコルバージョンは**変更しません**。ヘッダーは56バイト、payload形式も従来どおりです。`20..23` は `StreamId` UInt32 LE、`24..27` は `FrameIndex` UInt32 LE、`28..31` は `TimestampMs` UInt32 LE で、この判定に時刻は使いません。予約領域 `44..49` は引き続き0です。CRC32 は `0..51` を対象とし `52..55` に保存します。ウィンドウサイズもセッション ID も送信しません。他のフィールドは[フレームレイアウト](../concepts/protocol.md)を参照してください。既存送信側の変更は不要で、受信側の採用規則のみが変わります。

## `ResetDecodeDiagnostics()`

```csharp
public void ResetDecodeDiagnostics()
```

エラーログの出力予算と予測 readback・フォールバックのカウンターを初期化します。既存のフレーム・RPC カウンターと、順序判定に使う最後の適用ストリーム・フレームは初期化しません。

## 診断

| メンバー | 意味 |
| --- | --- |
| `lastFrameValid` | 最後のフレームはすべてのデコード ステージを通過しました。 |
| `lastHeaderValid` | ヘッダーはペイロードをデコードする前に有効でした。 |
| `lastError` | 最後のデコーダ エラーまたは警告テキスト。 |
| `lastNetworkMessageCount` | デコードされたネットワーク フレーム内で見つかったメッセージの数。 |
| `lastAppliedVariableCount` | 動作に適用される変数の数。 |
| `lastRpcCallCount` | ディスパッチされた RPC メッセージの数。 |
| `lastCodecId` | 最後の有効なヘッダーから読み取られたコーデック ID。 |
| `lastFrameIndex` | ヘッダーから読み取られるフレーム インデックス。 |
| `lastPayloadBytes` | デコーダによって使用されるペイロードのバイト数。 |

## 製本申請書

デコーダは、`TSMPSetup` によって生成されたバインディング配列を使用します。各バインディング マップは次のとおりです。

- `networkId`
- `variableHash`
- 値の型
- ターゲット行動
- 対象フィールド名
- 同期方向

変数メッセージが到着すると、デコーダーはそれを一致するバインディングにのみ適用します。 RPC メッセージが到着すると、デコーダはそれを一致する `TSMPNetworkBehaviour` にディスパッチします。

## ランタイムルール

- ヘッダーは有効だがコーデック ID が不明なフレームは無視されます。
- ターゲット動作の `ReceiveInterpolation.None` は、その動作では受信した値が無視されることを意味します。
- RPC 呼び出しはイベントのようなものです。トランスポートがフレームをドロップする場合は、エンコーダでリピート フレームを使用します。
- アップロードされたワールドではインスペクター フィールドが表示されないため、デコーダーは重要な実行時エラーをログに記録します。
